## 2026-07-26: Rebuild the cadence panel in code, and stop deploying a stale binary

Closed the two long-standing items that had survived many
attempts: the frame-rate / game-speed adjustment menu never
being reachable, and cutscene speed ignoring the rate controls.

### Why the menu never worked

Three independent defects, each of which alone was enough to
keep it invisible:

1. `Menus/ExtrasMenu.wnd` declared a full-screen opaque USER
   window as its parent and was pushed on the shell stack, so
   it could outlive the shell and persist into gameplay.
   `scripts/build/macos/deploy-macos-zh.sh` therefore refused
   to ship the layout on purpose, which meant the menu could
   never open at all: the layout file was simply not there.
2. Every `.wnd` `TEXT =` field resolves through
   `TheGameText->fetch()`. No `.csf` in any language carries
   labels for a port-specific panel, so all of them would have
   rendered as `MISSING: 'x'`. Shipping a loose `.str` is not a
   workaround either: it replaces the whole string table rather
   than merging into it, which would have wiped the Chinese
   translation.
3. Shipping a layout means shipping game data, which has to
   land in the real game directory as well as the deploy
   directory to be visible.

### Fix: build the panel programmatically

`GeneralsMD/.../GUICallbacks/Menus/ExtrasMenu.cpp` was rewritten
to construct its own windows with `winCreate` /
`gogoGadgetStaticText` / `gogoGadgetSlider` /
`gogoGadgetPushButton`, and to own its own `WindowLayout` the
way the in-game options screen does. That removes all three
defects at once: no game data to deploy, no string-table
dependency, and full control over geometry.

Details worth recording:

- Labels use `TheGameText->FETCH_OR_SUBSTITUTE(...)` with an
  English fallback, so a translation can be dropped in later
  without the panel breaking today. This works because
  `ENABLE_GAMETEXT_SUBSTITUTES` is 1.
- Fonts come from `TheHeaderTemplateManager` rather than being
  hardcoded to Arial. The Chinese `HeaderTemplate.ini` replaces
  Arial with the localized face, so hardcoding it would have
  produced missing glyphs.
- Geometry is authored against the 800x600 reference and scaled
  by a **single uniform factor** (`min(xScale, yScale)`), and
  the font point size is scaled by the same factor. This is
  deliberately unlike `parseScreenRect` in
  `GameWindowManagerScript.cpp`, which scales x and y
  independently (stretching 800x600 layouts on 16:9) while
  `parseFont` passes the literal point size straight through
  with no resolution adjustment. That pairing is why stock
  menus look stretched and their text looks small at 4K.
- Live values are applied from `GSM_SLIDER_TRACK`, not polled
  from the layout update callback. `runUpdate` is only driven
  from `Shell.cpp` (shell stack) and `InGameUI.cpp` (layouts
  registered via `registerWindowLayout`), and a self-owned
  layout opened from the shell is covered by neither.
- The panel parent swallows mouse messages in
  `ExtrasMenuInput`, so a click on a slider cannot also start a
  drag-select box in the tactical view underneath.

Nothing in the panel touches simulation state. The render cap
is presentation only, and `FramePacer::setLogicTimeScaleFps` is
explicitly ignored in network games, so replays and multiplayer
cannot desync from this panel.

### Cutscene speed

The four rate hotkeys were silently dead during scripted
cinematics: `CommandTranslator::translateGameMessage` destroyed
every message while `TheInGameUI->getInputEnabled()` was false,
which is exactly the cutscene case. Added
`isPresentationMessage()` as an allowlist for the toggle and
the four rate keys, so presentation settings remain adjustable
while gameplay input stays correctly blocked.

### Bugfixes found along the way

- The render cap no longer chases the logic rate. Both
  `ExtrasMenu.cpp` and `SDL3Main.cpp` used to do
  `renderFps = max(renderFps, logicFps)`, which silently
  discarded the user's frame-rate choice whenever game speed
  went above it. The fixed-step accumulator already runs as
  many logic steps per rendered frame as the ratio needs, so a
  4.0x simulation at 60 render frames is simply 4 logic steps
  per frame and perfectly legal.
- Slider readback rounds instead of truncating. Values stored
  as `Real` (camera pitch, scroll speed, draw distance) came
  back one lower than they went in: 105 stored as `1.05f`
  reads back as 104.99998, which floored to 104, so the slider
  drifted down by one every time the panel opened.
- Removed `GXCinematicSpeedTenths` / `GX_CINEMATIC_LOGIC_FPS`.
  Nothing ever consumed them; a separate cutscene logic rate
  was never wired into the frame pacer, so the option only
  looked like it worked.

### Deploy: the stale binary

The desktop launchers `cd` into the real game directory, which
keeps its own copy of the binary and dylibs next to the `.big`
archives. The deploy script only ever updated the throwaway
runtime directory, so the launchers had been starting a build
from 17 July while testing happened against 26 July. Any fix
verified in the test directory looked broken when launched
normally.

`deploy-macos-zh.sh` now mirrors the engine payload (binary,
dylibs, ICD manifest, `dxvk.conf`, `run.sh`, `fontconfig/`,
`fonts/`) into additional install directories: any listed in
`GX_MIRROR_DIRS`, plus auto-detection of a sibling directory
containing `.big` assets so it cannot fall behind again.
Licensed assets, the loose `Data` tree, saves and replays are
never touched. The mirror also filled in
`libdxvk_d3d8/d3d9`, which the real game directory had been
missing entirely.

Deleted `GeneralsZH/Data/Window/Menus/ExtrasMenu.wnd` and the
Linux deploy step that copied it.

### Validation

`DEBUG_LOG` compiles to a no-op in RelWithDebInfo
(`DEBUG_LOGGING` is only defined for DEBUG / INTERNAL), and
macOS refuses to deliver synthetic keystrokes to this SDL app
(neither System Events `keystroke` nor a raw key code reaches
it, confirmed by SagePatch's F11 screenshot hotkey also not
firing). Verification therefore drove the panel in-process
through a temporary self-test, since removed.

Confirmed, windowed at 1440x900 and fullscreen at native
4096x2304:

- Panel and all fourteen widgets construct; no asserts, no
  crashes, clean exit.
- Uniform scaling holds: 570x366 centred at 1440x900
  (scale 1.50), 1459x936 centred at 4096x2304 (scale 3.84).
- All five sliders apply through the real `GSM_SLIDER_TRACK`
  path and read back exactly what was set.
- Render cap and logic rate stay independent: game speed 4.0x
  left the 120 FPS cap untouched.
- Defaults button restores every row exactly.
- ESC closes; open/close cycles repeatedly with no leak.
- Ctrl+G binding registered as expected: `key=MK_G(37)`,
  `modState=CTRL(4)`, `transition=DOWN`,
  `usableIn=COMMANDUSABLE_EVERYWHERE`.

The one link not verified end-to-end is SDL delivering the
physical Ctrl+G keypress, which this environment cannot
synthesize. The binding is registered correctly and the handler
it invokes is verified, so that step needs a human at the
keyboard to confirm.

## 2026-07-26: Localize the panel and put the clarity switch in it

Two additions to the cadence panel: Chinese captions, and a
runtime switch between the two scaling paths.

### Chinese captions

The engine has no `LANGUAGE_ID` for Chinese — the enum in
`Language.h` stops at Korean, because the Chinese release is a
translation patch shipping its own `Data/Chinese` tree rather
than a new language id. `GetRegistryLanguage()` is what actually
selects that tree (both `HeaderTemplate.cpp` and `GameText.cpp`
build their paths from it), so it is the honest detection signal
here too; `UserPreferences.cpp` already tests it the same way.
Confirmed returning `chinese` on this install.

Each caption now carries an English and a Chinese built-in
fallback, and a `.csf` label still wins over both, so a real
translation can be dropped in later without touching this code.

Two encoding facts worth recording, because both could have
produced mojibake and neither is obvious:

- `WideChar` is `wchar_t` here, and `UnicodeString::value_type`
  is `WideChar`. On macOS that is 4-byte UTF-32, so `L"中文"`
  literals are natively correct. There is a separate
  `WideCharWindows` (`uint16_t`) used only for network
  compatibility — the internal type is deliberately `wchar_t`.
  So no UTF-16 truncation trap, but only because the port made
  that choice; a `uint16_t` typedef would have silently
  corrupted every non-ASCII literal.
- The glyphs resolve because the deployed payload bundles
  `simsun.ttc` and `99-macos-fonts.ini` sets SimSun as the
  primary unicode font. The Chinese `HeaderTemplate.ini` names
  its faces in GB2312, which arrive as mojibake, but
  `W3DGameFont`'s fallback path maps them onto SimSun. Since
  the panel takes its faces from `TheHeaderTemplateManager`
  rather than hardcoding Arial, it inherits that for free.

### The clarity switch

The two scaling paths were previously selected only by how the
game was launched. There is now a row in the panel naming the
active mode and the resolution it produces, with a button that
switches to the other one:

- **native HiDPI** — render at the display's full physical pixel
  count. Sharpest, and the most expensive, because this engine's
  fixed-function pipeline is emulated and was written for
  1024x768.
- **point for point** — render at the logical point size and let
  the swapchain upscale. On a 2x display that is an exact
  integer doubling, so it stays clean rather than resampled, at
  a quarter of the pixels. This is what Windows games get when
  they opt out of DPI virtualization.

The percentage is derived from the live density rather than
assumed to be 50, so a 1.5x scaled mode gives 67 and a non-HiDPI
display gives 100. The row is not built at all when density is
1.0, since both modes would render identically and the control
would visibly do nothing.

Applying live is fullscreen only, and deliberately so: in
windowed mode `SDL3Main` already treats the configured
resolution as physical pixels and sizes the window to
`resolution/density` points, so the window *is* the pixel grid.
Re-applying a render scale there would just resize the user's
window, which is not what a clarity switch should do. Windowed
therefore saves the preference and says so rather than pretending
to have applied it.

The live path reuses the stock options screen's sequence,
including both `onResolutionChanged` notifications — skipping
those leaves fonts and the cursor at the old scale. A rejected
`setDisplayMode` is reported and leaves the mode alone instead
of being treated as success.

Because the render resolution changes underneath the panel, the
panel is torn down and rebuilt at the new scale. Doing that from
inside the button's own handler is safe for the same reason the
Close button is: `winDestroy` only unlinks and queues onto the
destroy list, and the free happens later in
`processDestroyList`, so gadget code touching the clicked button
after the handler returns is touching valid memory.

### Validation

Same in-process approach as above (keystrokes still cannot be
injected). Fullscreen on the 4096x2304 panel:

- `registryLanguage='chinese' isChinese=1`.
- The Chinese caption survives end to end as codepoints
  `6E38 620F 901F 5EA6` — exactly 游戏速度. Logged as codepoints
  rather than bytes so that neither stderr encoding nor the
  terminal locale can be blamed for a passing result.
- Metrics: `points=2048x1152 pixels=4096x2304 density=2.00`,

- Switch applied live: 4096x2304 -> 2048x1152, panel rebuilt
  from 1459x1121 at (1318,591) to 729x560 at (659,296) — half
  size, still centred, new window object.
- Switching back restored 4096x2304 and left
  `GXRenderScalePercent = 100` as found.
- Instrumented click counting confirms one handler entry and one
  mode application per click, with the button pointer changing

- Zero asserts or crashes; clean run afterwards with the

Windowed at 1440x900 behaved as designed: preference updated, no
resolution change, no rebuild, and the panel reports that the

## 2026-07-26: Give the panel a slider thumb and real buttons

Two reported defects in the cadence panel: the bottom button row
overflowed the panel, the buttons had no button artwork behind
their text, and the sliders had no visible thumb. All three turn
out to be the same kind of problem — code that asks the shipped
data for artwork that is not in it, or that uses constants
authored for 800x600 without scaling them.

### The default gadget look asks for images that do not exist

`assignDefaultGadgetLook` looks up `PushButtonEnabled`,
`HSliderEnabledLeftEnd`, `HSliderThumbEnabled` and friends
through `winFindImage`. None of those names are defined as a
`MappedImage` anywhere in the retail `.big` archives — a search
across all of them returns nothing. They only ever appear inside
`.wnd` layouts, which carry their own artwork in their draw data,
so the retail menus never needed the defaults to resolve.

A panel built in code has no `.wnd` to inherit from, so every
lookup returned null. With `WIN_STATUS_IMAGE` set,
`W3DGadgetPushButtonImageDraw` routes to `...DrawOne`, which
draws nothing at all when its image is null. Hence bare floating
text where a button should be.

What does exist in `INIZH.big` is the three-piece set the retail
menus use: `Buttons-Left` (45x40), `Buttons-Middle` (10x40),
`Buttons-Right`, plus the matching `Buttons-Pushed-*`,
`Buttons-HiLite-*` and `Buttons-Disabled-*` families. The panel
now assigns those itself, which puts `...DrawThree` on the draw
path: caps at native width, middle tiled across the span. One
trap worth recording — the plain `GadgetButtonSetEnabledImage`
clears the middle and right slots, so the Left/Middle/Right
setters have to be used, and they have to run after
`assignDefaultGadgetLook`, not before.

There is no `HSlider*` family in the data at all, only `VSlider*`
and `ScrollBarThumbEnabled`. So the horizontal sliders ask for
the colour renderer on purpose by leaving `WIN_STATUS_IMAGE`
clear, and set track and thumb colours explicitly. This is not a
fallback; there is no image path available to prefer.

### The thumb was always there, at 13x16

The thumb is not missing. `gogoGadgetSlider` creates it as a
draggable child push button. It was invisible for the same
`WIN_STATUS_IMAGE`-with-null-image reason as the buttons, and it
was sized from `HORIZONTAL_SLIDER_THUMB_WIDTH` (13) and
`HORIZONTAL_SLIDER_THUMB_HEIGHT` (16) in `Gadget.h`, which are
authored in the 800x600 reference space and never scaled. On a
4096x2304 panel that is a 13 pixel thumb on a 1414 pixel track.

Two approaches were rejected. Changing the constants touches
list boxes, combo boxes and vertical sliders, and would restyle
every stock `.wnd` slider in the game. Editing `gogoGadgetSlider`
would do the same to every caller. Instead
`GadgetHorizontalSlider.cpp` now reads the thumb's live geometry
wherever it previously assumed the constants: two helpers,
`thumbWidthOf` and `thumbYOf`, feed the hit-testing in
`GGM_LEFT_DRAG`, the tick spacing in `GSM_SET_MIN_MAX` and
`GGM_RESIZED`, and every `winSetPosition` that used to hard-code
`HORIZONTAL_SLIDER_THUMB_POSITION` for its Y. At the stock size
every helper returns the stock constant, so existing sliders are
untouched.

The panel then resizes its thumbs to fill the track height and
re-sends `GSM_SET_MIN_MAX`, because `gogoGadgetSlider` had already
computed `numTicks` against the stock 13 and the travel would
otherwise disagree with the reported value.

Two bugs fell out of reading that code closely:

- At maximum value, `GGM_LEFT_DRAG` backed the thumb off by half
  its width, landing it somewhere `GSM_SET_SLIDER` would not put
  it for the same value. Six pixels at the stock size and easy
  to miss; at a scaled thumb it is a visible gap that makes the
  slider look like it never reaches its maximum. Now it lands
  flush.
- `GGM_RESIZED` forced the width back to `GADGET_SIZE` and left
  `numTicks` scaled against the old track, so a resized slider
  reported the wrong value for a given thumb position. It now
  keeps the thumb's width and rescales with it.

An earlier design had the thumb taller than the track with a
negative Y so it would overhang. That cannot work:
`GameWindowManager.cpp` clips a dragged child to its parent's
box, so the overhang would be destroyed on the first drag. The
thumb sits exactly as tall as the track at y=0.

### The button row arithmetic

Three 110-wide buttons with two 12-wide gaps is 354 design units
against a content width of 348, so the row hung over both
margins. The panel is now 400x308 instead of 380x292, and three
112-wide buttons with two 12-wide gaps is 360 against 368.

### Validation

Instrumented in-process at 4096x2304, then removed. All five
sliders came out 1414x57 with a 57x57 thumb and
`travel = 1414 - 57 = 1357`, and `numTicks * (maxVal - minVal)`
equalled 1357 on every row, so thumb travel and reported value
agree. All four buttons reported a non-null middle enabled
image, which is what selects `DrawThree`, and the three
`Buttons-*` lookups all resolved. Buttons measured at x=77..507,
553..983 and 1029..1459 inside the content span 61..1475 — no
overflow. Clean run afterwards with the scaffolding removed and
no residue in the log.

One incidental note: a mid-session log line reading `logic=30 fps
speed=1.000x` against an `Options.ini` holding
`GXGameSpeedTenths = 22` was a stale log, not a bug. The clean
run reports `render=60 fps logic=66 fps speed=2.200x`.

## 2026-07-27: A money trainer, the resize handler that was never written, and a real app entry point

Three things: the panel got a sixth row for editing cash, the
clarity switch was made to actually do something in windowed
mode, and the double-clickable app is now built by a script
instead of by hand.

### The money row

One function, as asked: a 0..500000 slider that sets the local
player's cash. It is a sixth row on the Ctrl+G panel, which grew
from 308 to 342 design units to hold it — one `ROW_STRIDE`, with
everything below the rows shifted down by the same amount.

Money is not like the other five rows. The other five are render
and cadence settings: local, cosmetic, and outside the
simulation. Money is *in* the simulation — it is part of the
lockstep model and it is CRC'd, so writing it in a network game
would desync the match and writing it during playback would
invalidate the replay. `trainerMoney()` is the gate, and it
returns null in LAN and internet games, during replays, and in
the shell, where the "local player" is whoever owns the menu
background map and there is nothing to cheat in anyway. Skirmish
is allowed: local game, AI opponent, no peer to disagree.

Where the row is inert the slider is disabled and the label says
`仅单人游戏可用` rather than showing a plausible `$0` that does
nothing when dragged.

Two smaller decisions:

- The edit goes through `deposit`/`withdraw`, not
  `setStartingCash`. `setStartingCash` zeroes the 60-entry income
  ring buffer, which would blank the sidebar's cash-per-minute
  readout. Both calls pass `playSound = FALSE` and
  `trackIncome = FALSE`, so the edit does not announce itself
  with the money chime or show up as earnings.
- The row is excluded from both Save and Defaults. Persisting it
  would mean a "preference" that silently hands the player cash
  every session, and resetting a player's cash to zero is not
  restoring a default — it is a destructive edit one misclick
  away from losing a game.

### "分辨率没跟上" — two separate bugs

The report was that switching clarity modes in a window did not
move the resolution, and that a window claiming 1440x900 made no
sense for this monitor. Both observations were right, for two
unrelated reasons.

The first: `applyScaleMode` bailed out immediately in windowed
mode with the comment "windowed is already point for point". It
saved `GXRenderScalePercent`, reported "已保存，全屏或下次启动时
生效", and left the window untouched — so the button looked
broken because it *was* broken. Windowed mode renders the
configured `Resolution` as physical pixels, so what the mode
selects is how many points those pixels occupy: density-for-one
at 100%, one-for-one below it. That is a window resize, not a
resolution change, so nothing needs rebuilding and
`GeneralsX_ApplyRenderScaleToWindow` just tells the window its
new size. The window's on-screen size is held fixed by folding
the percentage into the density divisor — without that, a switch
to 50% on a 2x display would shrink the window to a quarter of
its area and look like the button resized the user's window
instead of changing what is drawn into it.

The second was found while verifying the first, and was the more
serious of the two. `SDL3GameEngine::handleWindowEvent` was an
empty TODO stub, and the window is created
`SDL_WINDOW_RESIZABLE`. So DXVK's swapchain followed the window
while the engine's render resolution stayed wherever launch left
it, and `DX8Wrapper`'s pillarbox path stretched the difference.
The instrumented run said it plainly:
`winPoints=1395x925 winPixels=2790x1850` with
`Pillarbox: game=1440x900, backbuffer=2790x1850, present=2790x1850`
— the entire frame upscaled about 1.94x. That is exactly the blur
all the HiDPI work exists to remove, and it was arriving through
a window frame macOS had restored from a drag in some earlier
session. Implementing the handler — re-derive the render
resolution from the window's real pixel size, honour the clarity
percentage, notify `TheHeaderTemplateManager` and `TheMouse` the
way the stock options screen does — makes the pillarbox a no-op
again. Fullscreen is left alone; that transition is owned by
`SDL3_ApplyWindowModeForRenderConfig` and reacting to the sizes
Cocoa reports mid-animation would fight it.

The 1440x900 itself was not a display mode at all. It is the
stored `Resolution` preference read as render pixels, which is
neither the screen's resolution nor the window's size on screen.
The mode label now says which window mode is active and reports
both numbers, `renderPixels → windowPoints`, so it cannot be
misread that way again.

An incidental find: `Options.ini` held
`GXRenderScalePercent = 50`. Only `applyScaleMode` writes that
key, only on a button click — so that value was the fingerprint
of the reported bug, recorded in the preferences file. Reset to
100.

Verified live by driving a resize with AppleScript mid-run:
`window resized to 2080x832 points, render resolution now
2080x832 (50%)`, then the same for 1200x768. Swapchain width and
render width agree afterwards.

### The app bundle

`将军：零点行动.app` existed but was assembled by hand in July, so
it carried a July engine binary and nothing in the repository
could rebuild it. Worse, its `CFBundleExecutable` named the
engine directly rather than the Cocoa launcher sitting next to it
— so a double-click ran the engine with no
`DYLD_LIBRARY_PATH`, no Vulkan ICD, no asset root and no cadence
variables. The launcher was present but unreachable except from a
terminal.

`scripts/build/macos/package-macos-zh-app.sh` now builds it:
compile `packaging/macos/GeneralsXLauncher.m`, take the engine
from the build tree (falling back to the deploy directory), take
the dylibs from the deploy directory, write the plist with the
launcher as the entry point, sign inside-out, and swap the new
bundle in only after its own `--check` passes.

It is deliberately a second script rather than a change to
`bundle-macos-zh.sh`. That one builds a portable, zipped,
English-named bundle that discovers assets at runtime; this one
builds the local launcher with the Chinese name and icon and this
checkout's `游戏文件/GeneralsZH` baked in. Having one script serve
both is what produced two divergent layouts to begin with.

Two things the packaging turned up:

- The launcher's asset paths were hardcoded to one machine's
  external volume. They are now `-D` defines the script supplies
  from its own location, with the old strings as defaults. This
  repository has already been relocated once, and it cost a build
  session to stale absolute paths in the CMake cache.
- `MoltenVK_icd.json` cannot live in `Contents/Frameworks`.
  codesign treats everything there as nested code and fails the
  whole bundle over a JSON file it cannot sign. It moved to
  `Resources` with its `library_path` rewritten to
  `../Frameworks/libMoltenVK.dylib`; the launcher checks
  `Resources` first and still falls back to `Frameworks` so older
  hand-built bundles keep working.

Launch verified from Finder: fullscreen comes up at
`Apple Retina internal resolution set to 4096x2304 (target
4096x2304, renderScale=100%)`, swapchain matches, pillarbox is a
no-op, shell renders.

## 27/07/2026 — Windowed HiDPI: the window stops deriving itself

Fullscreen was already right. This entry is about the windowed
path, which had a design error underneath it and three separate
bugs sitting on top.

### The design error

The window size was re-derived from the render resolution while
the render resolution was re-derived from the window size. At
100% the arithmetic round-tripped and it looked fine; at 50% it
did not. Dividing render pixels by the *percentage-scaled*
density asked Cocoa for a window of `renderWidth` POINTS — on a
2x display, twice as many pixels of window as the render target
held — so the game drew at double size and the window framed
only its top-left corner. Requests past the screen edge were
then clamped by macOS, the resize handler fed the clamped size
back in, and the pair ran away to 5140x2004.

The window's point size is now stored state, not a computation.
Exactly three things set it: a resolution pick, the user
dragging the window, and launch. The clarity percentage is
deliberately not one of them. The invariant everything derives
from:

    windowPoints = pickedResolution / density   (clamped to fit)
    renderPixels = windowPoints * density * percent / 100

At 100% `renderPixels` equals the window's pixel extent, the
pillarbox is a no-op, and output is genuine 1:1 HiDPI. At 50%
the render target is half-size per axis and the swapchain
upscales by exactly 2 — soft, but correctly sized and filling
the window, which is what a Windows game gets when it opts out
of DPI virtualization.

Telling the two kinds of caller apart is what makes this work.
A resize the user performed arrives with a render size the
current window already implies and wants the window left alone;
a resolution pick arrives with one the window does not imply and
wants the window changed. Comparing the incoming size against
what the current window would produce separates them without
either caller having to announce itself.

`dx8wrapper.cpp`'s `Resize_And_Position_Window` was a second
writer doing the same unit confusion — `ResolutionWidth/Height`
are physical pixels, and the SDL3 `SetWindowPos` shim forwards
them to `SDL_SetWindowSize`, which takes points. The `__APPLE__`
windowed branch now skips it, matching what the fullscreen
branch already did on SDL platforms. `SDL3_ApplyWindowModeForRenderConfig`
is the single owner of window size, with a re-entrancy guard,
because `setDisplayMode` resizes the window, which posts a
resize event, which calls `setDisplayMode`.

### Launch had to happen before the device existed

Fullscreen gets the clarity mode for free — SDL3Main injects
`-xres/-yres` already scaled. Windowed mode kept the preference
verbatim, so a saved 50% was ignored until something resized the
window. Applying it afterwards with a `setDisplayMode` is not an
option: the base `Display::setDisplayMode` dereferences
`TheTacticalView`, which `GameClient::init` does not create until
after `TheDisplay->init()` returns, so it segfaulted on every
windowed launch at 50%. It now happens inside `W3DDisplay::init`'s
retry loop before `Set_Render_Device`, so the device is created
at the reduced resolution and there is no reset at all.

### The notifier owed more than it paid

`GeneralsX_NotifyResolutionChanged` sent only the header-template
and mouse notifications. Every `.wnd` layout and the control bar
are laid out in render pixels and cached at the resolution they
were built for, so a live 50% -> 100% switch doubled the render
target while the shell was still sized for the old one — the
"windowed HiDPI looks wrong" symptom. It now does what the stock
options screen does: `recreateWindowLayouts`,
`recreateControlBar`, `refreshCustomUiResources`, and the
tactical-view reset, all null-checked because a windowed launch
reaches the resize path before any of them exist.

### Cocoa clamps one axis, not both

`SDL_SetWindowSize` takes the content size, but the screen has to
hold content plus title bar. A request that fills the usable
height overflows by the bar's 32 points, and Cocoa answers by
shrinking the height alone: 1838x1034 came back as 1838x1002,
turning 16:9 into 1.83:1. `SDL_GetWindowBordersSize` cannot
reserve the bar in advance — asked before the window is on
screen it reports zero on all four sides. So the frame is
measured instead of predicted: read back what was granted,
rescale the untouched axis by the same ratio. One pass, not a
loop — the second request is strictly smaller, so there is
nothing left to clamp.

### The Resolution preference was rewriting itself

Two writers, both storing a render size where a picked
resolution belonged. `handleWindowEvent` stored the *scaled*
target into `m_xResolution`, so at 50% every window resize
silently halved the saved resolution. And `oldDispSettings`
captured `TheDisplay->getWidth()`, which is the render size below
100%, then `DeclineResolution` wrote it back. Both now record
the picked value.

### The window that grew on its own

At 100% the window widened by a few hundred points at a time
until it was wider than the display, and the render target
derived from it clipped the picture. This one did not get a root
cause, and the entry should say so.

What was ruled out, by instrumentation rather than reasoning:
breakpoints on `SDL_SetWindowSize`, `-[NSWindow setFrame:display:]`,
`setFrame:display:animate:` and `setContentSize:` were never hit
across full runs, yet the growth still arrived as ordinary Cocoa
resize events. SagePatch only ever sets position, and only on a
hotkey. DXVK's SDL3 WSI `resizeWindow` is called from
`dxgi_swapchain` only, and this is a D3D9 title. Both live
`SetWindowPos` call sites are compiled out on macOS. macOS window
restoration is not involved — no saved state, no frame autosave.

So the cause is unfixed and the symptom is bounded instead:
`SDL_SetWindowMaximumSize`, set from the **full display bounds**.
AppKit refuses the oversized frame itself, before any event is
posted, so there is nothing to react to — which matters, because
answering it from the resize handler means resizing a window in
response to a resize, and that is how the original runaway
started. Verified: three minutes at `Resolution = 4096 2304`,
100%, window steady at 1781x1002 points / 3562x2004 pixels with
exactly one resize — the launch one — and geometry unchanged at
the end.

The value was originally the usable bounds *less* the title bar,
which is the obvious choice and the wrong one — see the letterbox
entry below. Display bounds still catch what this was for, since
the growth ran past the display width.

Worth noting what turned out *not* to be bugs. `GXRenderScalePercent`
appearing to reset had no phantom writer: it is a plain static,
and the only in-process writer is the panel's mode button. And
`stored=0x0` in the diagnostics was an artifact of `&&`
short-circuiting past `GeneralsX_GetWindowPointSize`, not lost
state.

### Clarity mode persists on Save, not on toggle

The mode button used to write `Options.ini` on every press, which
made a throwaway experiment permanent — the mode you happened to
leave the panel in became the mode you launched in, with no way
to back out. Every other row in the panel already works the other
way round: the slider moves the live value, Save commits it. The
mode button now follows the same rule, `savePreferences` writes
the live percentage, and `getScaleMode` reads the live value
rather than the file, since the file is now the *saved* mode and
no longer answers "which mode am I in". Verified: a run applied
50% live while the file stayed at 100.

### An empty TEXT field was fatal

`ToggleQuitMenu` segfaulted every time, in `_platform_strlen`
under `parseText`. The cause is data, not the menu code:
`QuitMenu.wnd` and `QuitNoSave.wnd` are the only two layouts that
declare a placeholder label as `TEXT = "";`, and they are the only
two that crashed. `readUntilSemicolon` strips the semicolon and
the leading space, so the buffer handed to `parseText` is exactly
two quote characters. Skipping the opening one leaves a string
that is nothing but separators, `strtok` answers `NULL`, and the
unguarded `strlen` dereferenced it.

An empty label is valid data, so the fix treats it as such: clear
the string and return `TRUE`, because the window is real and its
remaining fields still have to be parsed. The scan for the opening
quote is now bounded too — it used to walk memory until it happened
to find a quote, so a field with none would run off the end of the
buffer instead of failing. The fix stays inside `parseText`;
`strtok` appears about thirty more times in that file with the same
missing guard, but no other field has an empty value in shipped
data and widening the change would mean auditing all of them.

Verified in a real session: `-file "Maps\Bitter Winter\Bitter
Winter.map"`, ESC, and the menu renders all five buttons with the
Chinese labels intact. ESC again closes it, and the process exits
with no `.ips` written.

### The ISSUE144 traces are gone

57 `[GX-ISSUE144]` sites across nine files, all of them
instrumentation for a font-fallback bug that is closed. They were
never gated, so a release build wrote every one of them, and the
worst offenders were not merely noisy: one fired per delegated
glyph inside `Get_Char_Data`, others per frame for tooltips and
drawable captions. Each was a `sprintf` into a 512-byte stack
buffer followed by an `fprintf`, so this was a throughput cost as
much as a log-volume one.

Filtering at the sink was the tempting fix — `SDL3Main` already
drops these lines on iOS — but that still pays for formatting the
string before discarding it, and it hides the traces without
removing them. They are deleted at the source instead; git holds
the history if the font work ever reopens. One line survived as a
real diagnostic: FreeType failing to select a Unicode charmap is a
genuine one-shot failure, so it stays, reworded as a plain
`WARNING`.

Removing the calls orphaned thirteen `log_buffer` declarations and
one block that had lost its `sprintf` and was printing an
uninitialized buffer, plus an `else if` branch in
`LoadUnicodeFallbackFont` whose entire body was a log line. All
removed. The strip is deletion-only — no surviving statement
changed — and the log for a 55-second run now contains zero
matches, with the remaining bulk being the INI loader and FFmpeg's
swscaler.

### Fullscreen was already toggling; nobody was listening

Asked whether fullscreen switching and cursor release existed, the
honest answer was one of each.

Cursor release turned out to be complete: `Mouse` keeps a bitmask of
reasons not to hold the cursor, and the SDL3 event pump feeds it all
four macOS window events — focus lost and gained, pointer entering and
leaving. Four policy bits in `Options.ini` decide which contexts
capture at all. What was missing was a way to ask for the cursor back
while staying in the game. In fullscreen that mattered: SDL never posts
`MOUSE_LEAVE` for a fullscreen window because there is nowhere to leave
to, so the grab only broke when the game lost focus. `Cmd+G` is now a
fifth block reason, `CursorCaptureBlockReason_UserReleased`. Making it
a reason rather than a bare `releaseCapture()` is the whole point — a
plain release would be undone by the next `refreshCursorCapture()`, and
those fire on focus and mode changes, so the cursor would snap back on
its own. It is claimed ahead of the keyboard device so the `G` never
reaches the game, since `G` is a stock hotkey and `Cmd` is a modifier
the game does not use.

Fullscreen switching was the more interesting one, because
`Ctrl+Cmd+F` and the green zoom button already worked. The window is
created `SDL_WINDOW_RESIZABLE` and SDL3 uses native fullscreen Spaces
on macOS, so Cocoa performed the whole transition. The engine simply
never found out. It kept the render resolution it had in the window
while DXVK's swapchain grew to the panel, so the pillarbox stretched an
1802×1002 frame across 4096×2304 — a 2.27× upscale, blurrier than the
50% clarity mode it was supposedly rendering at. `TheDisplay` also
still reported windowed, which is wrong for anything that asks:
`Mouse::canCapture` picks its rule by window mode.

So the fix reacts rather than transitions. `GeneralsX_OnFullscreenChanged`
runs on `ENTER_FULLSCREEN` / `LEAVE_FULLSCREEN`, which arrive after the
animation has settled, and re-derives the render resolution for
whatever size the window ended up at, at whatever clarity percentage is
in force. Going in, that is the panel's pixels scaled by the
percentage; coming out, the window's — and macOS restores the frame the
user had before, so the stored point size is still the right thing to
derive from.

Getting there took one wrong turn worth recording. The first version
called `setDisplayMode` without further precaution, and `setDisplayMode`
calls `SDL3_ApplyWindowModeForRenderConfig`, which sets the SDL
fullscreen state again — and `SDL3_EnsureNativeFullscreen` pumps events
while doing it. One keypress produced four alternating transitions, and
the leaving path fought Cocoa's frame restore down from 1802×1002 to
2048×1034 points. The existing re-entrancy guard did not cover this,
because it only stops the resize handler; the apply function still ran.
A second flag, `s_gxFollowingNativeFullscreen`, makes that function a
no-op while the engine is following a transition macOS already
performed. The window is right; only the render target is not.

Measured after the fix, one keypress gives one transition: 1780×1002
windowed → 2048×1152 fullscreen with a 4096×2304 backbuffer, which is
an exact 2× upscale at 50%, and back to 1780×1002 with the window at
its original size. Zero errors, no crash report, and `Cmd+G` toggles
correctly in both modes.

### The black bars were the window's own ceiling

Fullscreen had a band of black across the top and the bottom, and
everything that reports a size said it should not. The render
resolution was 2048×1152, the DXVK swapchain was 4096×2304, the
pillarbox line agreed, and the panel is 4096×2304. Nothing in that
chain is wrong, which is why the previous session's fix was aimed at
the wrong thing.

`SDL_SetWindowMaximumSize` is the cause, and the reason it is hard to
see is that it is not a window API by the time it reaches Cocoa.
`Cocoa_SetWindowMaximumSize` (`SDL_cocoawindow.m:2694`) implements it as
`-setContentMaxSize:`, and AppKit applies a content maximum to the
window's **fullscreen** content as well. The ceiling was the usable
bounds less the title bar — 2048×1002 points here — so the fullscreen
drawable came out 4096×2004 inside a 4096×2304 panel, and the 300
spare rows were split above and below. Exactly the observed bars.

Clearing the ceiling on `ENTER_FULLSCREEN` does not work, and this was
measured rather than assumed: a deliberate round trip with the clear in
place still logged `drawable 4096x2004`. The event is posted *after*
Cocoa has sized the fullscreen frame, and a native toggle — `Ctrl+Cmd+F`
or the green button — offers no earlier hook, so there is no moment at
which reacting is possible. Only the ceiling's *value* can prevent it.

So the ceiling is now the full display bounds. It cannot clamp a
fullscreen that is exactly the display size, and it still does the job
it was added for, since the runaway growth ran past the display width.
Keeping a window inside the *usable* area is a separate concern, handled
by the fit-to-usable rescale and by `GeneralsX_EnsureWindowTitleBarOnScreen`.

Two consequences fell out of reserving the title bar in the right place
instead. The fit-to-usable rescale now subtracts the bar before
computing the scale factor, so its first request is satisfiable and the
aspect-restore pass has nothing to undo. And the clamp-learning test had
to move to the frame — `(requestH + bar) >= usableH` — because the old
content-against-usable test can no longer fire once the bar is reserved
up front, which would have quietly frozen the measured bar at its seed.

The diagnostics are kept, at the user's request, and annotated with what
they are for. One line where the ceiling is set, reporting its value;
one line per fullscreen transition, reporting the drawable next to the
render size, the point size, and the ceiling actually in force. The
mismatch between drawable and panel *is* the letterbox, and neither line
is in a hot path. If bars are ever reported again, compare the two.

Verified end to end on a rebuilt binary: clean launch at `drawable
4096x2304, max 0x0`; a native round trip through windowed and back with
the title bar reachable at frame `245, 30, 1803, 1034`; and a screen
capture measuring `4096x2304  black rows: top=0 bottom=0`. Rows were
counted as near-black all the way across, 64 samples per row, because
the game's own art has dark regions a naive average would call a bar.

### Leaving fullscreen by the green button left windowed mode wrong

Reported plainly: switching out with the native button gave a window
that was "a bit strange". It was three separate defects stacked, which
is why it looked like one vague wrongness rather than a bug.

First, `IsWindowed` was dropped on the reset path. Re-deriving the
render resolution goes through `Set_Device_Resolution`, and that path did
not carry the windowed flag forward, so the engine came out of
fullscreen still believing it was fullscreen. Anything that branches on
window mode branched wrong — `Mouse::canCapture` among them, which is
why the cursor behaved oddly in the restored window.

Second, `LEAVE_FULLSCREEN` sized from a window that had not been
restored yet. Cocoa posts the event during its own restore, so reading
the window size at that moment returns the fullscreen size or an
intermediate one, and the render target was derived from it. The handler
now defers, logs `left fullscreen: awaiting restored window size`, and
derives on the resize that Cocoa sends when the frame is actually back.

Third, the window ceiling reserved no title bar, so the restored frame
could sit with its bar above the top of the screen — content 1579×1066
at frame `y = -62`, nothing left to grab. That measurement is where the
32-point figure came from, and `SDL_GetWindowBordersSize` cannot supply
it: the Cocoa backend does not implement it and reports zero on all four
sides for a window plainly showing a bar. So the bar is seeded at 32 and
only ever raised from what Cocoa actually does, on the one honest
measurement available — a height request Cocoa refuses. Reserving a few
points too many costs a few points of window; too few costs the title bar.

### The hidden menu bar could not be reached with the cursor released

`Cmd+G` released the cursor in fullscreen, but moving it to the top of
the screen did not reveal the menu bar — which is what a macOS user
reasonably expects, since that is how every other fullscreen app behaves.

The reason is that the app was not asking for a hideable menu bar; it was
asking for the bar to be gone. SDL sets `fullscreen_exclusive`
(`SDL_video.c:1947`) whenever `SDL_GetWindowFullscreenMode()` is
non-NULL, and the Cocoa backend answers
`-willUseFullScreenPresentationOptions` with
`NSApplicationPresentationHideMenuBar` in that case. That is a hard hide:
no amount of hovering brings it back, because there is nothing to reveal.

Two changes together. The window now goes fullscreen non-exclusively —
`SDL_SetWindowFullscreenMode(NULL)` before the transition — which is
correct on its own terms here, since the game renders at the panel's
native size and never wanted a mode switch. And
`SDL_HINT_VIDEO_MAC_FULLSCREEN_MENU_VISIBILITY` is toggled with the
cursor: visible while the cursor is released, hidden again when it is
recaptured. The hint's `"auto"` setting is not usable for this, because
auto means *visible only if fullscreen was entered via the title-bar
button* — and the engine enters it programmatically at launch.

Verified by capture at the top of the screen in both states, with the
transitions counted by log line number rather than by tailing. That
detail mattered more than once during this work: `osascript` delivers
duplicate keystrokes, and `set frontmost` can switch Spaces and re-enter
fullscreen on its own, so tail order does not tell you which transition
you are looking at.
